# Red same-root living-Pokédex setup recipes V1

Status: locally qualified successor contract; publication pending. This design is subordinate to
[MISSION.md](../MISSION.md), [NORTH_STAR.md](../NORTH_STAR.md), and the generated
[active product state](../ACTIVE_PRODUCT_STATE.md).

## Result first

The project can now describe and durably validate the kind of Red lesson the option-value model
actually needs: construct one authentic decision origin, save it once, restore the exact same
bytes before every candidate arm, route only that arm, freshly observe its terminal, and ask the
real profile-bound provider whether the semantic option is executable. No candidate provider is
executed during setup validation, and no setup action becomes a learner target or outcome.

This replaces the earlier pre-observed catalog approach. The authenticated historical census had
only eight complete three-option menus—five train and three development—and did not have the
family or physical-location diversity required by the frozen 10+5 curriculum. More importantly,
the old adapter expected endpoint observations and offers to exist before their routes ran.
Cross-joining unrelated historical captures would have manufactured counterfactual choices. That
catalog path is retired; its code remains historical evidence, not the active source of lessons.

The new contract is infrastructure, not training data. Qualification used ROM-free fakes and
created **zero** authentic Red captures, behavior draws, learner labels, outcomes, predictions,
fits, authority promotions, or transfer results.

## Why the same-root fork matters

A useful menu asks a causal question: from this exact state, which genuine action is better? If
acquisition is observed in one save, storage in a second save, and evolution in a third, the model
cannot tell whether an outcome difference came from the option or from the starting state. A
same-root fork makes the comparison well-defined:

```text
authenticated root
        |
  bounded construction
        |
 exact saved origin
   /       |       \
restore  restore   restore
route A  route B   local C
observe  observe   observe
offer A  offer B   offer C
```

The three offers form one complete menu only when every branch begins from the same serialized
origin and every destination offer is freshly derived from the branch that reached it.

## Frozen recipe boundary

Before any controller input, one private recipe plan binds all fifteen prospective slots to:

- one unique authenticated root state and canonical progress envelope;
- one base boundary and one constructed decision-origin boundary;
- an optional semantic-router construction route;
- three ordered portable option kinds;
- one actual Red provider type and exact context profile per option;
- an optional semantic-router route from the shared origin to that provider;
- one prospectively declared transformation-family digest per provider; and
- ten one-to-one logical-to-physical origin-map scopes across the 10+5 schedule.

The plan rejects family overlap across logical family scopes before controller input. This is
deliberate: discovering after fifteen roots have been consumed that every evolution arm was the
same Diglett-to-Dugtrio family would waste the campaign and invalidate the intended split.

Route recipes hash the flattened execution acknowledgement contract, including `(y, x)`
coordinates, modes, transitions, transient positions, and terminals. They contain no raw button
sequence and cannot be labeled as a teacher route.

## Runtime validation

The durable campaign seals the whole recipe plan, then handles each slot as follows:

1. Create an exclusive episode and persist its claim before constructing a runtime.
2. Read and independently hash the exact source-root state and envelope bytes.
3. Construct the decision origin once and persist neither a path nor a public identity.
4. For each candidate, restore the same origin bytes with zero actions and require the entire fresh
   observation digest—not merely the same map coordinate—to match the captured origin.
5. Execute only the candidate's transport route, if any, under the setup budget.
6. Freshly observe the terminal and request the exact profile-bound provider offer with zero
   actions.
7. Require an available executable binding, exact provider/profile provenance, and the frozen
   transformation-family digest. Do not invoke its executor or verifier.
8. Restore the origin once more and require exact semantic equality.
9. Persist the exact repeatable origin state/envelope, option bindings, fork proofs, accounting,
   and immutable terminal privately; publish only aggregate counts and zero-effect claims.

Complete, failed, and interrupted claims are permanent. Restart may recover a terminal or continue
only a never-claimed slot. A power loss after a claim but before durable accounting becomes an
interrupted terminal with unknown setup totals; it never becomes permission to retry.

## What qualification falsified

The audit caught and repaired three concrete hazards before publication:

1. Red routes use `(y, x)`. The earlier feasibility fixture used diagonal coordinates, so swapping
   the order was invisible. Off-diagonal route tests now bind the actual execution convention.
2. The Diglett evolution profile builds `RedObservedGoalSkillProvider`, not
   `RedProgressGoalProvider`. The public capability provenance now names the class that really
   emits the offer.
3. Returning source-root digests was not enough. The validator now receives, hashes, parses, and
   canonicalizes the exact source-root bytes itself, and every candidate restore must reproduce the
   complete captured-origin observation.

Adversarial tests also reject cross-origin routes, coordinate/profile mismatch, family mismatch,
location aliasing, noncanonical or tampered private captures, unavailable offers, actionful
restore/offer calls, changed final restore, runtime-factory effects, incomplete accounting, and any
retry of a claimed failure.

## Honest remaining blocker

No authentic fifteen-recipe plan exists yet. The present evolution provider exposes one semantic
family—Diglett to Dugtrio—and the balanced-team provider exposes one generic one-level family.
Those static families cannot honestly satisfy the frozen train/development family separation when
the same kinds recur across several scopes. The next engineering gate is therefore not to press
buttons or fit a model. It is to define genuine target-specific, repeatable evolution and
development offers (and inventory the other provider families), then freeze a 15-slot recipe plan
whose expected family and ten-map joins pass before any root is claimed.

Trade remains a separate mission-level blocker. This first calibration may exclude trade, but no
living-Pokédex or cross-version authority claim may.

## Claim boundary

Supported after publication:

- same-root recipe and fork semantics;
- exact source-root and restored-origin authentication;
- prospectively frozen family and physical-location separation;
- durable claim-before-input and no-retry accounting;
- exact private capture recovery; and
- aggregate, path-free public reporting with zero learner effects.

Not supported:

- an authentic Red recipe plan or setup campaign;
- causal train or new development examples;
- a new model fit or model-controlled gameplay;
- a powered Red comparison or authority promotion;
- Crystal execution or transfer; or
- semantic trade and living-Pokédex completion.
