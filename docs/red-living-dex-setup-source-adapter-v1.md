## Result first

The repository now has a concrete, action-free Red adapter for one canonical private setup
catalog. The adapter requires the exact **10 train + 5 development** slot order, **45** available
semantic provider offers, **3 local + 42 routed** option bindings, and **14** distinct authenticated
route plans. It rereads and rehashes the complete catalog before every slot join and once more at
the materializer's final attestation, so one successful materialization performs **17 identical
source reads** and rejects any mid-read replacement.

The catalog producer accepts typed Red runtime evidence rather than arbitrary public rows:

- `FreshRedGoalObservation` joins one coherent Red observation to one ready traversal boundary;
- `RedGoalBindingOffer` must contain an available `ExecutableGoalBinding` for the declared goal;
- the provider class must be an exact member of the published Red capability allowlist; and
- every routed option must carry a nonempty `RoutePlan` whose origin, terminal, costs, traversal
  requirements, transitions, and planner binding are hashed as private evidence.

The producer never calls the executable or verifier. A later setup campaign remains the only layer
that may claim a slot and invoke one setup port. The adapter therefore creates no behavior choice,
learner target, outcome, model fit, or authority.

## Private construction and freeze boundary

The tracked implementation deliberately separates production from consumption:

1. An approved private integration gathers the fifteen authenticated slot witnesses. This step is
   outside the public artifact and must preserve the already-frozen slot order and partitions.
2. `build_red_living_dex_setup_source_payload` validates all typed evidence and emits one canonical,
   unique-key JSON byte sequence. It then constructs the complete private binding plan in memory so
   duplicate or aliased plan identities fail before a catalog can be accepted.
3. `freeze_red_living_dex_setup_bindings.py` accepts only a regular, current-user-owned,
   owner-private catalog outside the repository plus its exact SHA-256 and a validated private
   artifact root.
4. `RedLivingDexSetupCatalogSource` reopens and authenticates the exact bytes on every interaction.
   The published whole-plan materializer independently proves every protected-effect delta remains
   zero and seals only a complete fifteen-slot result.

The public terminal is aggregate and path-free. The canonical source contains private hashes but no
filesystem path, raw controller sequence, teacher route, behavior selection, outcome, or policy
target. File ownership and mode checks are defense in depth; the caller-supplied SHA-256 and repeated
whole-payload authentication remain the immutable content authority.

## Qualification boundary

The direct tests cover both the typed producer and the untrusted catalog decoder. They prove:

- exact 15/45/42 derivation without invoking any executable or verifier;
- route digests distinguish identical button traces with different costs or requirements;
- complete binding-plan construction rejects aliased state identities before publication;
- missing, reordered, duplicate, cross-joined, changed, synthetic, or teacher-derived evidence
  fails closed;
- source-protocol introspection cannot hide a controller-authority delta;
- noncanonical or duplicate-key JSON is rejected; and
- failures never repeat a private path or reader exception.

All qualification fixtures are ROM-free and synthetic. Passing them establishes implementation
quality, not the existence of one authentic Red plan.
