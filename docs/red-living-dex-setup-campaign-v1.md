## Why this exists

The published 10+5 Red curriculum identifies fifteen useful semantic decision states. The
published routed-semantic composer can preserve a selected destination kind while privately
travelling to its provider. Those pieces were still insufficient to press a button safely:

- fourteen lesson slots had no exact private route/terminal/provider joins;
- a structurally valid three-kind menu could still contain a fictional arm;
- no whole-slot worker durably consumed a setup before controller input; and
- a power loss could otherwise invite an accidental retry.

This module supplies the missing contract and runner. It does not supply the actual private Red
bindings. Synthetic ROM-free fixtures prove the boundary, not the cartridge facts.

## Frozen private binding shape

Every one of the fifteen prospective slots receives exactly one private slot binding. It joins:

1. the original slot, setup-plan, terminal-predicate, observer-contract, and partition digests;
2. one repeatable root, expected captured state, origin boundary, envelope, menu, observer binding,
   family rows, and location;
3. the complete ordered option-kind menu; and
4. one option binding for every menu row.

Each option binding preserves the portable option kind and its exact goal-kind mapping. It names an
implemented Red provider contract and the already-published capability digest. A local option must
stay at the captured boundary and may not carry route fields. A routed option must leave the origin
boundary and bind an exact semantic-router plan, route-terminal predicate, planner provenance,
fresh destination observation, provider offer, and executable binding. Raw direction sequences and
teacher routes are structurally forbidden.

The canonical Red census remains **one locally composable slot and fourteen routed slots**. The
private binding plan must retain the exact order and all **10 train + 5 development** identities.
It also rejects reused roots, states, envelopes, menus, observer bindings, and routed plans.

Plan construction proves only structural binding. Its public projection says private runtime
bindings are **not authenticated** and private routes are **not executed**. Authentication requires
the separately gated private plan and setup run.

## Execution order

One campaign pass follows this order:

1. validate the exact canonical Red prospective plan;
2. seal the entire private fifteen-slot binding plan;
3. acquire the exclusive campaign session;
4. inspect or recover the next deterministic slot namespace;
5. create and synchronize the exclusive partial episode—the one-shot claim;
6. synchronize the exact claim record;
7. confirm plan sealing and claiming changed no controller/frame counter;
8. call the private setup port once;
9. reconcile its self-report against an independent action/frame meter;
10. verify the exact capture attestation and all option proofs;
11. persist the execution and complete artifact; and
12. publish a separate immutable terminal.

There is no behavior commitment, selected arm, learner label, outcome observation, prediction,
teacher query, or fit anywhere in that sequence.

## Durable terminal rules

| Situation | Permanent result | Retry |
| --- | --- | --- |
| Valid setup and complete option proofs | Complete, with exact capture attestation and measured budget | No |
| Sanitized expected failure | Failed, with reason and measured budget | No |
| Invalid result, proof mismatch, or unexpected exception | Failed after claim, retained under a finite safe reason | No |
| Process interruption caught in-process | Interrupted terminal with measured budget, then interruption propagates | No |
| Orphan partial found after power loss | Interrupted terminal; exact action/frame accounting is marked unknown | No |
| Existing complete/failed/interrupted terminal | Recovered and verified; setup port stays closed | No |

An over-budget attempt is recorded with its actual overage and consumed. It is not erased because
the shared qualification will reject it. A recovered complete artifact must contain the exact
original claim as well as a valid execution; a plausible-looking execution alone is insufficient.

An orphaned power-loss terminal remains useful no-retry accounting, but its unknown exact budget
prevents shared inventory qualification. The runner never manufactures zeroes. A later private
campaign may continue only with never-claimed slots.

## Complete-menu proof

A successful setup returns the existing title-neutral
`LivingDexCaptureAttestation` plus one action-free option proof per ordered menu row. The join checks
all of the following against the frozen slot:

- slot, setup, terminal, observer, root, state, envelope, menu, and location;
- option kinds and family bindings in exact order;
- measured setup actions and frames;
- option-binding identity;
- fresh destination observation;
- authenticated provider offer; and
- executable destination binding.

No unselected semantic option executes during setup. The proof says that the option is genuinely
bindable; the later system-random selected-arm materializer remains the only layer allowed to draw
and execute one learner choice.

## Public boundary

The public plan and run views expose only aggregate counts: partitions, local/routed option counts,
terminal statuses, known/unknown budget-accounting totals, and protected-effect zeroes. They omit
slot IDs, root/state/location identities, route plans, terminal boundaries, observations, provider
offers, executable bindings, episode IDs, private paths, and controller sequences.

## What this milestone can and cannot establish

It can establish that the repository has a restart-safe, no-retry implementation capable of
accepting an exact private fifteen-slot plan without crossing the learner boundary.

It cannot establish that any private Red route exists, that all fifteen authentic states can be
materialized, that a setup succeeded, that a causal example exists, that the model improved, or
that anything transfers to Crystal. The learning counters therefore remain unchanged.
