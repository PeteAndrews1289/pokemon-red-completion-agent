## Where to inspect the data

These are additions to the existing player journal and decision files, not a
second logging framework. New native executions record them automatically when
their existing recorder is present; standalone semantic tests may use the same
optional read-only hooks. Old missing encounters cannot be reconstructed.

| Question | Record and useful fields |
| --- | --- |
| Why this goal instead of another? | Each model-selected `step-*/selection-diagnostics.json`: actual scores/probabilities, model-version vectors, normalization, raw and clipped outcomes, signed utility terms, economy adjustment, largest raw feature contributions, feature differences and runner-up margin. |
| What choices never reached the model? | `native/diagnostic-events.json`: regional source exclusions, topological estimates, route evaluation starts, offered sources with resource quotes, configured exclusions, and separate unexamined sources after an enumeration cap. |
| Why did it flee or fail to catch? | Survey decision events: actual species, required species, missing quantities, registered entries, storage, directive and reason. Separate verified captures, direct flees and unsuccessful capture attempts; old `flees` retains its legacy combined meaning. |
| What did the inputs actually change? | Boundary/event states and each step's outcome diagnostic delta: cash, bag quantities, Repel, capture headroom, retained specimen XP/levels/HP/status/moves and new registrations. Unknown readings remain null; a delta does not invent its cause. |
| Was the observation incomplete? | Boundary `unknown_fields`, current and maximum decoded party PP, control ownership/visible text, readiness and whether native battle history exists. A newly connected history starts empty; old losses are not fabricated. |
| What data did the learner really receive? | `TRAIN-COVERAGE.json`: authenticated retained source counts, settled versus censored attempts, successful and failed targets by kind, feature range/variance/nonzero coverage, weighted features, clipping and in-sample residuals. No fit or automatic admission. |
| What mechanics can inform future scenarios? | `CARTRIDGE-FACTS.json`: all 151 species' types, base stats, catch rates, base XP, growth codes, learnsets and TM/HM compatibility; every decoded wild map's ordered slots, levels and distinct grass/water rate bytes. |
| Where does wall time go? | Step phase timings and native costs: observation/menu construction, selection receipt, diagnostics, execution, verification and terminal observation; durable diagnostic-write time is reported separately. |

`MECHANICS-DETAILS.json` adds starting moves, all165 move powers/PP/accuracy/
effects/priorities and225 type pairs from the already pinned mechanics catalog.
`BATTLE-REVIEW.json` reuses the existing read-only battle risk and aftermath
adapters. The original run result is not rewritten after reviewing it.

The existing trainer battle episodes and `battle_choice_review.py` remain the
source for attack/switch choices, usable PP, matchup risks, actual outcomes and
local battler identity. They are not replaced by a second combat recorder. Their
schema-specific review must only be applied to compatible retained episodes.

Scores are regression estimates, not calibrated win/capture probabilities;
runner-up margin is not confidence. Top feature contributions explain the raw
linear prediction before clipping, not causal effects of interventions. Training
residuals are in-sample, and constant/nonzero features do not prove generalization.
Encounter rate bytes are not per-step probabilities and slot probabilities are
not assumed equal. Cartridge classroom facts, private binding identities and
diagnostic deltas are not new final-actor features. Hidden reserve opponents, raw
addresses and future RNG state are deliberately not added to the actor.

Read the declared plan and result first, then align event action/frame ordinals
with the existing action trace and decision. A failure can retain sealed events
without a final survey report. Never convert these DEVELOPMENT diagnostics to
TRAIN labels or count better logging as parameter learning.
