refits. Test model-owned preparation and challenge selection using the existing

## Findings by priority

### P1 — consequential options are removed before learned ranking

The private completion runner supplies phase order and preparation through
`stage_from`, `strongest_field_lead`, `league_preparation_assembly` and
`assembly`. Its fixed League targets include Blastoise 65 and Snorlax 35.
Priority branches frequently replace the menu with one binding and mark other
goal kinds unavailable. Its outer story inventory omits the optional member
preparation callback.

The collection connection additionally supplies ordinary-before-prize ordering,
some supply quantities, source/segment-specific income reassessments and forced
recovery/corridor offers. These actions were useful development support, but a
model choosing from their reduced menu does not own those earlier decisions.

**Consequence:** increasing runtime budgets, scoring harder or refitting the
battler cannot teach a strategic choice that the runtime never offers.

**Reuse:** `NativeStoryBranchInventory`, plural preparation/story bindings and
`observe_native_player_options` already support fresh, real alternatives and
explicit support ownership. Use them in the next pilot; leave the closed helpers
and their historical evidence unchanged.

### P1 — the successful whole-game composition is not a canonical autonomous entry

The public continuous native runtime is reusable. However, the completed

global substitutions, stage priorities and repair-specific gates.

The public collection CLI is not a supported launch path for this exact
whole-player workload: it rejects collection-continuation mode, and its separate

**Next dependency:** lift the accepted composition into one configured runtime
incrementally as learned ownership is connected. Preserve deterministic

rewrite, extra checkout or new orchestration framework.

### P1 — useful optional preparation can be absent after a genuine loss

The existing member-preparation API generates distinct temporary intents for
eligible combat/undecided members, preserves permanent field/collection roles
and uses measured XP. Its default dose is at most three levels.
A strongest-opponent reference is already available.

It also caps offered targets at the quoted opponent level. A retained Lorelei
loss has Blastoise 62, already above Lorelei's highest level 54. Level comparison
alone therefore cannot expose further carry preparation even after a real loss.

Prospective challenge features describe levels/counts, not matchup quality.
Battle-time type/effectiveness knowledge is not automatically a high-level
prediction of whether this party can complete the next challenge.

**Smallest permitted next change:** if confirmed on the pilot's actual menu,
add an explicit development-only opt-in to offer bounded training above that
reference after an observed defeat. Keep one- and three-level doses optional,
deduplicate targets and preserve legacy defaults. Do not force training, assign
a weakest-member priority, introduce a fixed 65/35 threshold or disable role,
state, cost or protection checks. A new representation is not presumed necessary;
first observe whether the existing ranking fails for lack of information.

### P2 — ordinary setbacks still need unattended recovery composition

It is not true that every failed goal terminates it. But unknown exceptions
still stop execution, and ordinary story battle loss can end a private segment
through `LoreleiStoryBattleStopped`. External repair/relaunch supplied continuity.

Keep illegal inputs, mismatched saves, stale bindings and unverified state fatal.
Normalize only independently verified ordinary lost-battle/blackout outcomes
into existing recovery and fresh selection, as needed in the focused pilot.
Do not suppress arbitrary exceptions or convert failed attempts into success.
