# Roadmap baseline and deviations

The stable reference is [baseline red-first-v1](../configs/development-roadmap-baseline-v1.json),
shown in the [development infographic](development-roadmap.md). The mission and North Star still
outrank this reference. Status can change after evidence; the destination and exit criteria must
not be silently rewritten to make the project appear further along.

## Baseline adoption — September 6, 2026

This records the user-agreed sequence, not a new product pivot: useful Red play, model-led story
completion and living collection, a compatible unfamiliar Red modification, Crystal, then later
games and a cross-title living collection. Older Crystal-first and powered-campaign roadmaps
remain historical. Existing teacher successes do not count as learned story completion.

## Recording a deviation

Before materially changing stage order, scope or exit criteria, append a dated decision here:
the prior plan, evidence or user request, proposed change, effect on the end goal, costs/risks,
and the decision owner. Preserve the previous baseline file and create a new version if its
meaning changes. A small implementation choice within an existing milestone is not a new baseline.

After each completed work session, append a concise review to the roadmap state: result,
deviation (or none), and next step. Refresh again within a long session after a material verified
fit, gameplay result, capability or blocker changes the project position. No heartbeat or
minute-by-minute rewrites are needed. Missing new learning is a fact to show, not a reason to
move the goalposts.
